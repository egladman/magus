# BZZ1007: unknown module member

A qualified access like `crypto\hash(...)` names a member the module does not
export. The name resolves to nothing, so at run time the call would fail with
`buzz: null is not callable` - or, worse, read as `null` and quietly flow on.

```text
[BZZ1007] buzz: line 167:11: module crypto has no member "hash"
  see: .../BZZ1007.md
```

## Resolution

Check the module's actual surface and use the real name:

```sh
magus describe module crypto
```

For a Buzz-source module, its exports are what carry the `export` keyword -
`export fun`, `export object`, `export enum`, `export final`, `export var`.
A member without `export` is private to the defining file and is not reachable
through the namespace even though it exists in the source.

Typical causes, in the order they are usually true:

- A typo, or a name from a different module's API.
- A member that was renamed or removed. `fs\mkdirall` became `fs\mkdirAll`;
  `os\exec` moved to `proc\exec`.
- An API imagined rather than looked up - a plausible-sounding name that the
  module never had.

## Why this is an error rather than a guess

A namespace built from a module's exports used to treat any miss as an untracked
export and return `Unknown`, because exported `final`/`var` declarations were not
collected and so the member list was genuinely incomplete. They are collected
now, which makes the namespace complete and the miss real.

The cost of the old behavior was concrete: `crypto\hash(crypto\HashAlgorithm.Sha256, ...)`
sat in a spell's AWS SigV4 signing path, naming a function and an enum that the
crypto module has never had. It type-checked, and nothing ran that file, so it
was found by reading rather than by any gate.
