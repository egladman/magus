# BZZ1008: redundant import alias

`import "<path>" as <alias>;` binds `<alias>` unless nothing was written after
the path, in which case the import binds the path's last segment instead. For
some import kinds that is the whole story, so when `<alias>` is spelled exactly
that segment the `as` clause changes nothing:

```text
[BZZ1008] buzz: line 3:1: import alias "codex" is redundant, drop `as codex`
  see: .../BZZ1008.md
```

```buzz
import "spells/harness/codex" as codex;   // BZZ1008: drop `as codex`
import "spells/harness/codex";            // binds `codex`, same result
```

## Magusfiles and embedded Buzz only

This check fires only in EMBEDDED mode: the REPL, `magus eval`, and magusfile
loading. A session opts into it with `WithEmbedded()`; `NewSession` alone parses
upstream-strict, and strict mode never flags this. `"spells/"`, `"project/"` and
`"magus/spell/"` are magus's own dialect, unknown upstream, so only `"buzz:..."`
can appear in upstream Buzz at all - and upstream's own suite writes
`import "buzz:math" as math;` idiomatically (`tests/behavior/math.buzz`,
`os.buzz`). Flagging it there would make gopherbuzz reject valid upstream
programs, which breaks the "strict superset of upstream" claim this library
makes; gating on embedded mode is what keeps both true at once.

## Which imports this applies to

Only a `"spells/..."`, `"project/..."`, `"magus/spell/..."`, or `"buzz:..."`
import can be flagged. Each of those resolves to a single VALUE the same way
whether or not it is aliased (resolveImport in `session.go` never branches on
`imp.Alias` for them), so a same-spelled alias is provably inert.

Every other import (a plain relative or bare `.buzz` FILE, such as
`"./tools/drift"` or `"badge"`) is never flagged, even when the alias repeats
the path's last segment:

```buzz
import "badge" as badge;   // NOT redundant, even though the names match
```

For a file import, aliasing is not just a name choice: it switches
resolveImport from FLAT-MERGING the file's globals into the importing scope to
executing it in an ISOLATED sub-session reachable only through the alias. Bare
`import "badge";` splats badge's exports straight into this file's scope (and
would let magus mistake them for this file's own targets); `as badge` keeps
them behind the `badge\...` namespace. Dropping the alias there is a real
behavior change, not a no-op, so the diagnostic does not touch it.

## Resolution

For a flagged import, drop the `as <alias>` clause; the import still binds
under the same name.

A rename is only real when the alias differs from the last path segment:

```buzz
import "spells/harness/claude-code" as claude;   // not redundant: "claude-code" != "claude"
```

`as _` is never flagged. It requests upstream's flat import (every export
splatted into scope, unprefixed), a different binding shape than a named
alias, not a spelling of the default name.
