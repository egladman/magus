# MGS4011: undeclared file written

A target finished successfully, and a file under its project's directory was
created, or an untracked one changed, while it ran. No target declares that
file with `ctx.writesFiles`, as an output or as an in-place edit.

```text
[MGS4011] proto:breaking wrote 1 file it does not declare: proto/report.txt;
declare them with ctx.writesFiles([...]), or write them outside the tree
```

The message names up to five files and says how many more there were.

## Why this fails the run

A target that declares no outputs could mean two things: it writes nothing, or it
writes files and forgot to say so. Nothing outside the run can tell them apart.
This check settles it. A target that declares no outputs and passes wrote
nothing, so it is a check.

A file no target declares is outside the cache's model. A hit does not replay
it, `magus clean` does not remove it, and the affected set cannot say who
reads it.

## Fixing it

**Declare the output, when producing it is the target's job:**

```buzz
import "magus";

export fun report(ctx: magus\Context, args: [str]) > void {
    ctx.writesFiles(["report.txt"]);
    // ...
}
```

**Declare the edit, when the target amends a file that already exists:**
`ctx.writesFiles([...], editsExistingSource: true)`, the declaration
[MGS4007](MGS4007.md) describes.

**Or write it somewhere else, when it is scratch.** A temporary file belongs in
a temporary directory, not in the project's tree.

## What it checks, and what it does not

The check runs only after the target **succeeded**, and only when its body ran:
a cache hit replays declared outputs and runs nothing.

It compares each file's modification time and size before and after the run,
over the project's directory. It checks every file the run **created**, and
every file it **modified** that the VCS does not track. A tracked file is never
reported: a person saving `README.md` mid-run must not fail it, and a target
rewriting its own declared source is [MGS4007](MGS4007.md)'s finding. When the
VCS cannot say which modified files are tracked, the run logs an MGS4011 notice
naming them and does not check them.

It leaves out:

- the directories of projects nested inside it, whose own runs answer for them;
- the directories the source walk prunes: `.git`, `.magus` and the names in
  the project's ignore set, such as `node_modules`, `vendor` and `gen`;
- the tool caches a spell declares (`GOCACHE`, `GOMODCACHE`), wherever the
  environment points them, so a CI that keeps `GOCACHE` in the checkout works;
- a binary a target declares it replaces, with `relinks` in its policy;
- any directory holding its own checkout, such as a worktree kept in the tree;
- the files this magus process's standard output and error are redirected to;
- files any target in the workspace declares as an output, and files this
  target declares as an edit or a stamp.

A deleted file is not reported.

## Known limits

- **A file a person creates inside the project mid-run is blamed on the run.**
  Nothing tells a person's new file from the target's. Rerun; the run names
  the file.
- **A target that rewrites a tracked file it does not declare goes unreported**,
  unless that file is one of its declared sources, which MGS4007 checks.
- **Only declared caches are left out.** A spell's other writable sandbox
  locations, such as `$GOPATH/pkg/sumdb`, carry no environment variable to
  locate them by, so a write there inside the project is reported.

## Two targets running at once

Targets of one project share its directory, and a parent project and a nested
one can each write into the other's. So when a related target was running at
the time a file was written, as its modification time reads, the write is not
blamed on either. A related target declaring the file claims it. Otherwise the
run logs an MGS4011 notice naming the file and the targets that were running,
and does not fail. Run the target alone to see which one wrote it.

Another magus process cannot run a target of the same project at the same time,
since it waits on the project lock.
