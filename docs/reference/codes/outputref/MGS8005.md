# MGS8005: a cache hit replayed another checkout's log

The cache key names inputs, not the checkout that ran them. Checkouts of one
repository that share a store (linked worktrees, clones pointed at one cache dir)
hit each other's entries, and a hit replays the producer's log byte for byte. Each
entry's manifest records the checkout that produced it, and a hit compares that
root with its own.

A hit from another checkout is a notice:

```text
MGS8005: test/pkg:build replayed a log recorded in another checkout, /src/app; it names 0 path(s) under that checkout
```

It becomes an error when the replayed log names paths outside this checkout:

```text
MGS8005: test/pkg:test replayed a log recorded in another checkout, /src/app; it names 3 path(s) outside this checkout, /src/app-feature, so those lines describe that checkout's files, not these; `magus run --no-cache` records this checkout's own
```

Those lines point at files in the other checkout. Opening them edits the other
checkout's tree, which can differ from this one at any uncommitted change.

## What magus does about it

The hit stands and the log replays unchanged: rewriting paths inside a log would
change bytes a tool parsed, and could not be told apart from what the tool printed.
The hit records a new attempt under this run's own timestamp and lease, so the
output ref this run prints names this run.

Counting is one scan of the log per root. A checkout nested inside the producer's
root (a linked worktree under the primary) does not count its own paths as outside.

## Fixing it

- Run the target with `magus run --no-cache` to record this checkout's own log.
- Give the checkout its own store when its logs must name only its own paths.
