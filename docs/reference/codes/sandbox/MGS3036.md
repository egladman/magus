# MGS3036: a project's magusfile held whole

`magus job fork`, `magus job apply`, the `client` tool (`magus\job.put`) and a
magusfile's `magus\job.put` refused a job because one of its write paths names a
project's magusfile whole:

```text
[MGS3036] job: wave/slots holds a project's magusfile whole: "magusfile.buzz",
  such as `magusfile.buzz#project.name`, `magusfile.buzz#project.targets.test`,
  `magusfile.buzz#build`. Every job that changes the workspace's configuration
  writes that file, so a whole-file hold blocks them all for one line; claim the
  declarations and project keys the job changes instead
```

Nothing was written to the job store. A put that adds such a path to a job that
already exists is refused the same way and leaves the job as it was.

## Why

A target's slots, a source glob and a new spell import are each one line of a
magusfile, and every job that changes the workspace's configuration writes that
one file. A job that holds it whole serializes all of them behind its own line.
Claims split the file: the functions it declares by name, and the
`magus\project({...})` table by key path.

## Key claims

Inside the top-level `magus\project({...})` call, a claim names a key path:

- `magusfile.buzz#project.<key>` holds one top-level key, such as `project.sources`.
- `magusfile.buzz#project.<key>.<entry>` holds one entry of a key whose value is a
  map: `magusfile.buzz#project.targets.test` holds the `test` entry of `targets` and
  nothing else.

A claim on a key whose entries are placed (`project.targets`) names every entry, so
fork refuses it as ambiguous with [MGS3031](MGS3031.md). A key that does not exist yet
is accepted, since the job may be about to add it.

## What is refused

- A literal path to a magusfile a project loads: `magusfile.buzz` at the root or in
  any project, or a file under a `magusfiles/` directory.

## What is not refused

- **A claim** (`magusfile.buzz#project.targets.test`) or **a glob** (`**/*.buzz`). A
  job holding a magusfile through a glob narrows on its first write to the file: its
  row gains a claim on each declaration or key the write changes, and the rest of the
  file is recorded as released, with its digest. From then on the glob no longer
  holds that file for the job.
- **A checkout that cannot place the file's lines**: no `*.buzz diff=buzz` line in
  `.gitattributes`, or a version control that places none. Nothing smaller than the
  file could be claimed there.
- **`magus.yaml`.** No diff driver places its keys yet.
- **A spell source** a magusfile imports.

## The release request

When another live job holds the file, the refusal also opens one attention request
(outcome `waiting`) naming the holder and the file, with the claims the refused
fork wanted as its files. A second refusal over the same holder and file lands on
the same request. The holder narrows its write paths, or exits, and the holder or
the root closes the request:

```sh
magus session attention
magus session dispose <request>
```

## What to do

Claim what the job changes:

```sh
magus job fork wave/slots --write-paths 'magusfile.buzz#project.targets.test'
```
