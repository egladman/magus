# MGS3045: a ci gate over the write paths nothing runs

`magus job fork`, `magus job apply` and `magus\workspace().putJob` refused a job record
because `ci` runs a target over its write paths that the job never runs:

```text
[MGS3045] ci runs `lint .` over the write paths (it reads changes/**/*.md), and
  neither the check nor a postcondition runs it: add the postcondition
  {"id":"lint","kind":"check","check":{"target":"lint","project":"."}} to postconditions,
  or permit it in deviations
```

Nothing was written to the job store.

## Why

A job graded only on its check can pass while the gate that will judge its
change fails. The failure then surfaces after integration, where nobody holds
the files any more, unless the workspace names who runs the gate before the
job counts as landed. Then the record names that owner.

## Which project a gate names

A write inside a project gates on that project's target when its target reads
the file. A write under `libs/x` asks for `test libs/x`, and a check of `test .`
does not satisfy it, since the root's tests do not run the module's.

The root keeps a gate of its own over the file in two cases:

- The root's target spells the path out in its sources, as `libs/**/*.go` or
  `docs/reference/codes/**/*.md` do. Both targets then read the file, so the
  write asks for both. A bare `**/*.go` is a language default and spells out
  nothing.
- The project has no such target, or its target does not read the file.

A project binding spells it carries unresolved cannot say which targets it
runs. Its gate stays on the root, and the fork lists that project among the
checks it did not run.

A row is judged on the write paths each write adds. A live row keeps a deviation
naming `test .` over a sub-project write, and a re-apply adding no path is not
asked again. A record that adds a path there is asked for `test libs/x`.

## Who runs the gate

The problem is raised in every workspace. The fix it names depends on who
the workspace says runs the gate:

- `ci.remote_gate` in magus.yaml names a CI that runs `ci` on every pushed
  commit. The fix is a deviation whose reason is
  `<remote_gate> runs it`, such as `github-actions runs it`, and no
  postcondition.
- Otherwise, when the job's parent or an ancestor is an integration job,
  the fix is the deviation `the integrator runs it`.
- Otherwise the fix is the postcondition, so the worker runs the target.

A workspace that declares an owner makes the same choice for
[MGS3044](MGS3044.md): the fix permits the output for the integrator rather
than widening the write paths. A lint gate always gets its postcondition, since a
worker meets lint over the files it wrote. An integration job owns its gates,
so it gets the postcondition too.

The job then passes `magus job wait` on its own postconditions.

## The fix as data

A job problem in `-o json` carries the fix as data beside its prose: `postcondition` for the
last case, `deviation` for the first two. Magus never applies either. Merge
them into the record yourself:

```sh
jq '.postconditions += [.problems[].postcondition | select(.)] | .deviations += [.problems[].deviation | select(.)]'
```

Where `ci.remote_gate` names the owner, one deviation per target settles every project of it:
`{"code":"MGS3045","subject":"test *","reason":"github-actions runs it"}`. A lint gate is
exempt from globs, so it keeps one postcondition per project. A postcondition whose check the guard would deny
([MGS3040](MGS3040.md)) takes the deviation instead.

## What to do

- Add the postcondition the problem prints, so the worker runs the target.
- If the root runs the gate once after integrating every job, permit the
  problem with `<target> <project>` as its subject:

```json
"deviations": [
  { "code": "MGS3045", "subject": "lint .", "reason": "the root runs it" }
]
```

`magus describe job <id>` lists the gates not run and the postconditions to add.
