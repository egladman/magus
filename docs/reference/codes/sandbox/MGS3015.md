# MGS3015: run isolation wedged

One invocation shares an isolation gate: a step declared `exclusive` takes the
whole gate, every other step takes one seat. This fires when something is queued
for the gate, every step holding it is parked in a wait of its own, and nothing
in the run has started, finished or printed a line for the grace. magus refuses
the wait instead of spending it:

```text
[MGS3015] refusing to keep waiting for this run's isolation gate: every step holding it
  is itself waiting, nothing in this run has started, finished or printed a line for 30s,
  and what is queued cannot start until a holder finishes. Holding: . ci holds the shared
  side and is waiting on the targets it composes. Queued: . generate needs the exclusive
  side. A step waiting for the gate its own ancestor holds is the shape this catches;
  report it with the run's captured log, since no magusfile can produce it.
```

## The rule this protects

A run takes the gate **at most once per path**. Work dispatched beneath an
admitted step (a `ctx.needs` child, a composed target's skip-cache gate) runs
inside its ancestor's region and inherits that lease rather than queuing for a
second one. `exclusive` is a claim against BATCH peers, and the ancestor's own
admission already excludes every one of those, so inheriting gives nothing away.

The shape this code exists for is what happens when that rule breaks: a child
asks for the exclusive side while its own ancestor holds the shared side, waits
for a release that cannot come until it returns, and every later shared request
parks behind the queued exclusive one. On 2026-09-11 that held every project lock
for 19 minutes with `magus status` reporting nothing running and no child
process alive.

## What it usually means

**A magus defect, not a workspace one.** Unlike
[MGS3013](MGS3013.md), which names an authoring mistake a magusfile can fix,
nothing a magusfile declares can produce this shape. It exits 70 (EX_SOFTWARE),
and a wrapper retrying on EX_TEMPFAIL must not retry it.

## Resolve it

1. **Keep the captured log.** The failure line names it. The "Holding" and
   "Queued" lists in the message are the whole investigation: which step held
   which side, and what each was parked on.

2. **Report it** with that log and the targets involved. A reproduction is worth
   more than a bisect here: the shape is deterministic once a chain reaches it.

3. **Do not raise concurrency.** Nothing about this wait is a shortage of slots,
   and a wider pool changes only how many steps are parked behind it.

4. **To get moving again**, run the affected targets individually
   (`magus run <target> <project>`) rather than the composite that wedged. A
   single target still composes its chain and is not queued behind a batch peer.

## What it does not fire on

**A busy run.** A holder that is still working answers "not wedged" however long
it takes, which is what keeps a silent-but-busy step (a link, a test package that
prints only when it finishes) from being refused out from under a legitimately
queued exclusive step.

**A run nobody is watching.** The verdict needs the invocation heartbeat, so a
bare library `Cache.RunAll` with no heartbeat installed is never refused.

**An unlimited pool.** A limiter with no capacity keeps no per-step records, so
no holder can be shown to be parked and no verdict is reached.
