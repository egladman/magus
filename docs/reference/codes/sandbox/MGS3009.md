# MGS3009: machine budget exhausted

A step was not started. What it needs did not fit in this machine's build budget
alongside the claims other live magus invocations hold, and `budget_wait` did not seat
it. By default `budget_wait` is 0, so the step is refused at once:

```text
[MGS3009] not starting (root) ci: no seat is free, held by pid 41221 (root) test
  (10.0 GiB), in /Users/x/repos/magus-worktrees/polish. It did not wait, since
  budget_wait (--budget-wait, MAGUS_BUDGET_WAIT or magus.yaml) is 0; ... To wait for
  a seat instead, run the same command again with --budget-wait 30m, or set
  MAGUS_BUDGET_WAIT or budget_wait in magus.yaml
```

Waiting is opt-in. With `budget_wait` above 0, a claim that can fit waits in the
broker's queue whoever holds the room. It says so on stderr when it parks, and again
whenever the holders change, with how long it has waited and how long it has left:

```text
machine budget: waiting for a seat for (root) ci: it runs test, which claims 10.0 GiB
  (declared) and takes 6 slots, and 2.0 GiB of 48.0 GiB is left; held by pid 41221
  (root) test (10.0 GiB), in /Users/x/repos/magus-worktrees/polish. It gives up after
  30m0s (the bound budget_wait (--budget-wait, MAGUS_BUDGET_WAIT or magus.yaml) sets)
```

At the bound it asks once more, and is seated if room came free. Otherwise it is
refused, naming the holders at that moment and where the bound came from:

```text
[MGS3009] not starting (root) ci: waited 30m0s for a seat, held by pid 41221 (root)
  test (10.0 GiB), in /Users/x/repos/magus-worktrees/polish. That is the bound
  budget_wait (--budget-wait, MAGUS_BUDGET_WAIT or magus.yaml) sets; ...
```

`budget_wait` defaults to 0, the answer every claim got before 2026-11-05. Raise it with
`--budget-wait 30m`, `MAGUS_BUDGET_WAIT` or `budget_wait` in `magus.yaml`. When the run has a sooner deadline of its own (`magus run --timeout`,
`magus job exec --timeout`), that bounds the wait instead, and the line says so. A wait
on claims of the step's own process or its own run (the siblings of one fan-out) has no
bound and says nothing: those claims are work this run is already doing.

When one job's runs must get through while other jobs fill the budget,
`magus job pause <job>...` refuses those jobs' holders their next magus run until
`magus job resume <job>...`; a run already holding the budget finishes. Gates queue
first, in the order they asked; then a job's `weight` in (0,1] orders the rest, the
heavier first. Weight orders the queue and never decides a verdict. After four requests
go ahead of the head of the queue, nothing behind it is seated where it would take the
head's room.

A run under `magus job exec --timeout` shares the slots the wrapper holds. It gets no
more room than that, and a budget other invocations fill makes it wait like any run.

The code fires in three cases.

**The machine was full for as long as `budget_wait` allows.** The step above, at once
under the default of 0; the same command succeeds once a holder finishes.

**The declaration cannot fit at all.** No position in any queue seats a step whose
declaration exceeds the whole budget, so magus says so immediately rather than
waiting forever:

```text
[MGS3009] refusing to start (root) ci: it runs test, which declares 64.0 GiB, and takes
  8 slots, which does not fit in this machine's whole build budget of 48.0 GiB across
  8 slots. Waiting would not help; that budget is 75% of the memory available here; the
  rest runs the OS and everything else. Run `magus doctor` and read MGS1030, which
  compares this declaration to the peak memory magus measured: correct the declaration
  if it has drifted; if it is honest, get a bigger machine.
```

**A nested magus cannot tell who its parent is.** magus passes
`MAGUS_INVOCATION_ANCESTORS` to every magus it starts, and admission uses it to excuse
a run from the claim its own parent is holding. A magusfile that clears the environment
breaks that, and the affected run would be refused by a budget its own parent filled,
a permanent deadlock, since the parent cannot finish until this run does:

```text
[MGS3009] not starting docs ci: this magus runs underneath another one but was started
  without MAGUS_INVOCATION_ANCESTORS, so it cannot tell its own parent's claim from a
  stranger's and will not queue behind a run that is waiting for it; ... Pass that
  variable through to nested magus invocations, or let magus set it by not clearing
  the environment.
```

None of them exits 1, and they do not all exit the same way. A busy machine exits **75**,
`EX_TEMPFAIL` from `sysexits.h`, meaning "failed, try again later": the machine stayed
full for as long as `budget_wait` allows and the same command runs once it drains. The other two exit **78**, `EX_CONFIG`,
because no amount of retrying changes their answer. A declaration larger than the whole
budget and a nested magus with no ancestry both refuse identically on every retry, so a
wrapper that retries on 75 stops on those instead of looping. A run where real targets
also failed exits 1 as usual: a broken build does not become a scheduling problem
because a peer happened to be busy too.

## Why

The concurrency limiter is per-process. Every magus invocation admits work up to its
own capacity, and nothing sums those capacities, so N invocations across N worktrees
admit N budgets' worth of work against one machine. That is not a theoretical concern
on a developer machine running several agents at once: it is how a workstation ends
up tens of gigabytes deep in swap with every individual run comfortably inside its
own budget.

`memory_mb` is the declaration that makes this arbitrable, and the broker is what
arbitrates it. There is one broker per user, so there is one budget per machine:
every magus asks the same process, and the answer accounts for the worktrees this run
knows nothing about. A run starts the broker if none is up (and it exits by itself ten
minutes after it last held anything), because admission has no other arbiter; see
[the broker and the server](../../../guides/integrations/server.md).

It refuses at once unless asked to wait. Until 2026-11-05 a step another invocation kept
out was refused at once, and every caller then typed the same wait by hand: workers
piped `magus status --wait` into their checks, the checkout bootstrap wrapped every
nested run in it, `graph build` looped on it, and only the oldest `ci` gate waited in
the broker. The queue was already in the broker, so a claim that can fit waits in it
when `budget_wait` is set, and the refusal names how to set it. The default stayed 0:
a wait nobody asked for looks like work, so a caller opts in with `--budget-wait`, and
every wait then ends at `budget_wait`, naming who held the room. A cycle would need a holder waiting on a waiter, and a running step
waits only on its own descendants, which its free seat or its own run's claims let in
([ADR 0001](../../../decisions/0001-bounded-concurrency-with-recursive-invocation.md)).

The budget is derived from the memory the broker may commit, not from a reading of
what is free right now. That keeps the verdict deterministic: the same command on the
same machine reaches the same decision regardless of what a browser is doing, and the
message names figures a reader can check afterwards. Observed memory has two separate
jobs: the memory-headroom warning a run emits while it works, and the refusal of a new
step on a machine the kernel says is failing ([MGS3053](MGS3053.md)).

**A target that declares nothing claims what its runs measured.** Once a target has
three successful measured runs, its step claims 1.25 times the highest peak memory they
reached, and as slots the 75th percentile of their CPU time over wall time, rounded up
and capped at the run's width. The runs are the ones with the same charms and forwarded
args, or every run of the target when that shape has fewer than three. With fewer than
three it claims no memory and one slot: magus does not invent a figure it has not
measured. A replayed step runs nothing and claims nothing. Every step runs the Go
toolchain as wide as the slots it claims (`GOMAXPROCS` and `-p`), so a Go target's
measured width never exceeds its claim; declare `slots` to widen one.

**A composed target inherits its chain's largest declaration.** Only the target you
name is scheduled as a step. So `ci`, which composes `test` through `ctx.needs`, would
otherwise run the heaviest target in the workspace as if it had declared nothing, and
`magus affected ci` is exactly the invocation that fills a machine. The maximum rather
than the sum, because a chain runs its steps in order.

**A declaration always wins.** A declared `memory_mb` is a ceiling, and measured runs
size the claim under it: the same 1.25 times the measured peak, never more than the
declaration, and the declaration itself with fewer than three runs. So a
`-- -run TestOne` run claims what narrowed runs reach rather than what the whole suite
does. A declared `slots` is claimed as written. The refusal says how the memory figure
was sized, `declared` or `measured over N runs`, and `magus session -o json` records
each step's sizing.

**A run that loses the broker finishes, unless you said otherwise.** Under the
default `broker: best-effort`, a broker that dies mid-run takes its claims with it, the
run says once that it is no longer arbitrated, and it completes; its running steps
re-assert their claims on the next broker to come up. Under `broker: required` a step
that finds no broker is refused instead ([MGS3022](MGS3022.md)). Every claim rides its
run's connection to the broker, so a run that dies, even to `SIGKILL`, releases its
claims at once and nothing has to release cleanly.

## Resolution

1. **Free a holder, or raise the bound.** The message names the pid, project, target
   and directory holding each claim, and `magus server status` shows the whole budget and its
   waiters across worktrees. When the holder is work that should finish first, raise
   `budget_wait` (`--budget-wait 1h`, `MAGUS_BUDGET_WAIT`, or `budget_wait` in
   `magus.yaml`) and run the same command again. A rerun inside the minute meets the
   same holders. A leased worker files its check owed `no seat` instead.

2. **Check that the declaration is honest.** A `memory_mb` well above what the target
   peaks at holds up work that would have fit. `magus doctor` reports a
   declaration that disagrees with the peak resident memory magus has measured across
   recent runs ([MGS1030](../magusfile/MGS1030.md)), and that figure is the one to
   declare.

3. **Reduce what the target needs.** A suite that declares ten gigabytes because every
   concurrent test binary carries the race detector's shadow memory can often be
   sharded, or run with lower in-tool parallelism, and then declare less.

4. **Run on a bigger machine.** The budget is a fraction of what the host has, so a
   target that cannot fit on an idle machine is a target this machine cannot run.
