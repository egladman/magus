# MGS3053: the machine is short of memory

A new step was not started, because the kernel says memory is in a bad state right now:

```text
[MGS3053] not starting docs test: this machine is short of memory right now: the memory
  compressor holds 80% of its segment limit (973106 of 1216383), and a kernel panic on
  2026-10-31 came at 100%. Running steps keep going. Free memory, then run the same
  command again: `magus status` shows what magus holds, and this reading counts
  everything on the machine.
```

It reads:

- **macOS:** `vm.compressor.segment.total` against `vm.compressor.segment.limit`, refusing
  at 75%, and `kern.memorystatus_vm_pressure_level`, refusing at critical. A warning level
  does not refuse.
- **Linux:** `full avg10` in `/sys/fs/cgroup/memory.pressure`, else
  `/proc/pressure/memory`, refusing at 25%. `some` does not refuse.

Both figures are starting figures. The 75 rests on one panic and one healthy reading; the
25 has no Linux measurement behind it.

A step that replays from the local cache claims nothing, so it is never refused. A remote
hit still claims, and can be. A gate is refused like any other run: it does not wait. A
step that waited for a seat reads memory again once seated, and hands the seat back on a
bad reading.

A step already running is never stopped. A composer taking its claim back after its
members ran reads no memory, and a run nested under another magus passes, since refusing
it would fail the running step above it.

A missing reading (Windows and other hosts, or a Linux kernel without `CONFIG_PSI`) says
so once per run and starts the step. So does a partial one: macOS without readable segment
counts says so and goes by the kernel's level alone.

## Why

[MGS3009](MGS3009.md) arbitrates what magus's own targets declare and measured, and it
cannot see anything else on the machine. On 2026-10-31 a machine panicked with "73% of
compressed pages limit (OK) and 100% of segments limit (BAD)": Jetsam killed thousands of
small daemons and no magus process, and `watchdogd` stalled for 90 seconds. The budget had
nothing to say about that, and its verdict stays declared. This refusal sits in front of it.

## What it cannot tell apart

One reading has no rate and no owner, so this refusal is sometimes wrong.

- **A compressor full and flat, or full and climbing.** Cold idle apps and a climb toward
  a panic read the same. Guessed wrong one way, every run on that machine exits 75 until
  someone frees memory. Guessed wrong the other way, the machine panics.
- **This run's own spike, or pressure that stays.** A link step about to finish reads the
  same as other programs that will not. Guessed wrong one way, a `ci` gate fails on a
  member, perhaps far into its work, and a rerun replays what already passed. Guessed
  wrong the other way, more load lands on a failing machine.

Refusing is the choice because a wrong refusal costs a retry and a wrong admit costs the
machine.

## Fix

1. **Free memory**, in anything on the machine: the reading is not limited to magus.
2. **Run the same command again** once it has recovered. `magus status --wait` waits on
   the declared budget and does not see this. A job under a lease files the check as owed
   with `no seat` instead, unless it integrates: an integration owns its checks, so it
   frees memory and runs them again.

The guard refuses an agent the same command within a minute of this refusal, with or
without `magus status --wait` in front of it, since nothing has freed memory on its behalf.

**`broker: off` is the only way to turn this off.** There is no setting for this refusal
alone, so that also gives up the machine budget. Use it for a machine stuck in a state you
have judged harmless.
