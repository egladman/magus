# MGS1023: magusfile load failed

A project's magusfile raised an error while magus evaluated its top-level
code during workspace load - the step every command runs first, before any
target is selected. `magus ls`, `magus doctor`, `magus describe`, and
`magus run` all load the same way, so this fires the same way for all of
them.

```text
[MGS1023] project "api": magusfile load failed: magusfile: exec magusfile.buzz:
[MGS2002] fs write denied: /etc/escaped.txt
  see: https://eli.gladman.cc/magus/reference/codes/sandbox/MGS2002/
```

## Why

A magusfile is arbitrary Buzz: top-level statements run immediately when the
file is read, not only when a target is dispatched. That is deliberate (it is
how `magus.project(...)` and similar declarations work), but it also means a
mistake at the top level - a sandbox-denied filesystem call, a bad import, a
runtime error in a helper the file calls unconditionally - fails the whole
workspace load rather than one target.

Before this code existed, that failure still happened, but the message a
reader saw depended entirely on what the underlying cause happened to say.
A sandbox denial named its path; a plain runtime error did not always say
which magusfile was responsible. MGS1023 is the same failure wrapped with one
stable, pointable code, so "the workspace would not load" is never a bare,
uncoded string.

## Resolution

1. Read the wrapped cause first - it is preserved in the message and via
   `errors.Is`. A sandbox denial (MGS2001/MGS2002/MGS2007) names the exact
   path or command; resolve it the way that code's own page describes.
2. If the cause is a plain Buzz runtime error, the file and (when available)
   line are in the wrapped message; fix the top-level statement it points at.
3. Top-level code should stay minimal - declarations and simple
   configuration, not I/O or long-running work. Move anything heavier into a
   target body, which only runs when actually dispatched.
